## 1. فهم النظام (Understanding of the System)

### 1.1 الوصف بجملة واحدة

نظام يستقبل صور إقامات سعودية، يستخرج منها البيانات آلياً عبر OCR، يطبّق عليها مجموعة قواعد أهلية قابلة للتكوين، ثم يُصدر لكل إقامة قراراً (`APPROVED` / `REJECTED` / `MANUAL_REVIEW`) ويجمع النتائج في ملف تصاريح.

### 1.2 السياق التشغيلي كما أفهمه

النظام أداة **فرز مسبق (pre-screening)** تخدم جهة تُصدر تصاريح (دخول موقع، عمل، مقاول باطن...) وتحتاج التأكد من ثلاثة شروط قبل إصدار التصريح: الإقامة سارية، صاحب العمل ليس فرداً، والمهنة ليست ضمن المهن المستثناة.

### 1.3 ما هو النظام — وما ليس هو

| النظام **هو** | النظام **ليس** |
|---|---|
| أداة استخراج بيانات + تطبيق قواعد | مصدراً رسمياً للتحقق من صحة الإقامة |
| فرز آلي يُسرّع القرار البشري | بديلاً عن الجوازات / أبشر / مقيم |
| مُنتج ملف تصاريح قابل للتدقيق | كاشفاً للتزوير (forgery detection) — خارج النطاق ما لم تطلبه |
| يقرأ ما هو **مطبوع على البطاقة** | يقرأ ما هو **مسجّل في أنظمة الدولة** |

> ⚠️ **تمييز جوهري:** البطاقة قد تكون سارية شكلاً وقت الطباعة لكن الإقامة مُلغاة/هارب في أنظمة الجوازات. الصورة لا تكشف ذلك. هذا **قيد أصيل** في أي نظام قائم على الصورة وحدها، ويجب أن يُذكر صراحةً في مخرجات النظام ("الفحص مبني على البطاقة، وليس على الأنظمة الرسمية").

### 1.4 الأدوار (Actors)

| الدور | الصلاحيات |
|---|---|
| **Operator** | رفع الصور، تشغيل المعالجة، تصدير التقارير |
| **Reviewer** | كل ما سبق + تصحيح الحقول واعتماد حالات المراجعة اليدوية |
| **Rules Admin** | تعديل قواعد المهن/أصحاب العمل/العتبات |
| **Auditor** | قراءة سجل التدقيق فقط، بدون رؤية بيانات كاملة |

⚠️ عدد المستخدمين ونموذج الصلاحيات يحتاج تأكيداً (سؤال Q9).

### 2.4 التحقق من البيانات — Validation

| ID | المتطلب | أولوية |
|---|---|---|

## 3. المتطلبات غير الوظيفية (Non-Functional Requirements)

| المجال | المتطلب | القيمة المقترحة |
|---|---|---|
| **الأداء** | زمن معالجة الإقامة الواحدة (محلي) | ≤ 5 ثوانٍ ⚠️ Q7 |
| | حجم الدفعة الواحدة | حتى 500 صورة ⚠️ Q7 |
| | المعالجة | متوازية، عدد العمال قابل للتكوين |
| **الدقة** | استخراج الحقول الحرجة (رقم الإقامة، تاريخ الانتهاء) | ≥ 95% ⚠️ يُعاير بعد اختبار العيّنات |
| | **معدّل الخطأ من النوع الأول (قبول غير مؤهل)** | يجب أن يقترب من الصفر — النظام مُصمَّم ليخطئ باتجاه المراجعة لا القبول |
| **الموثوقية** | فشل صورة واحدة لا يُسقط الدفعة | إلزامي |
| | استئناف الدفعة بعد انقطاع | مرغوب |
| **الأمان** | تشفير البيانات الحساسة عند التخزين | AES-256 |
| | إخفاء رقم الإقامة في السجلات | `2*****789` |
| | لا إرسال خارجي بدون إعداد صريح + موافقة | إلزامي |
| **الخصوصية** | حذف الصور بعد المعالجة | افتراضي، قابل للتكوين |
| | حق الحذف الكامل (بيانات + صور + مشتقات) | إلزامي |
| **قابلية التدقيق** | سجل تدقيق لكل عملية | غير قابل للتعديل |
| **قابلية الصيانة** | تعديل القواعد بدون مبرمج | إلزامي |
| | تغطية الاختبارات | ≥ 80% للمنطق الأساسي |
| **قابلية النقل** | تشغيل محلي كامل بدون إنترنت | إلزامي (وضع Local) |
| **التدويل** | واجهة عربي/إنجليزي + دعم RTL | ⚠️ Q10 |
| **قابلية التوسع** | SQLite → PostgreSQL بدون تعديل منطق | إلزامي |

## 5. توصية منهجية الـ OCR

### 5.1 المقارنة

| المحرك | العربية | الحقول المهيكلة | محلي | التكلفة | الخصوصية | التقييم |
|---|---|---|---|---|---|---|
| **Tesseract** (`ara`) | ضعيف على البطاقات | لا | ✅ | مجاني | ✅ ممتاز | غير كافٍ منفرداً |
| **PaddleOCR** | جيد | لا (يحتاج layout) | ✅ | مجاني | ✅ ممتاز | **الأساس المحلي** |
| **EasyOCR** | متوسط | لا | ✅ | مجاني | ✅ ممتاز | بديل احتياطي |
| **Vision LLM** | ممتاز | ✅ نعم مباشرةً | ❌ | لكل صورة | ⚠️ نقل خارجي | **الأدق — بشروط** |
| **Azure / Google / Textract** | جيد–ممتاز | ✅ | ❌ | لكل صورة | ⚠️ نقل خارجي | يحتاج تقييم إقامة البيانات |

### 5.2 التوصية: بنية Provider قابلة للتبديل + وضعان تشغيليان

```
                  ┌─────────────────────────┐
   صورة مُعالَجة →│  OCRProvider (interface) │
                  └───────────┬─────────────┘
                ┌─────────────┼─────────────┐
        LocalProvider   VisionLLMProvider   CloudProvider
        (PaddleOCR)     (اختياري/بموافقة)   (اختياري)
                └─────────────┼─────────────┘
                     ExtractionResult موحّد
                     (حقول + ثقة + bbox)
```

| الوضع | المحرك | الاستخدام |
|---|---|---|
| **Local Mode** (افتراضي) | PaddleOCR فقط | بيانات لا تغادر الجهاز إطلاقاً — الامتثال أولاً |
| **High-Accuracy Mode** | Vision LLM | يُفعَّل صراحةً بعد موافقة موثّقة وتقييم PDPL |
| **Consensus Mode** | الاثنان معاً | الاتفاق → ثقة عالية · الاختلاف → `MANUAL_REVIEW` تلقائياً |

**لماذا هذا التصميم:** الدقة والخصوصية في تعارض مباشر هنا. بدل أن أختار عنك، أعزل القرار خلف واجهة واحدة فتستطيع تبديله بسطر تكوين — و`Consensus Mode` يمنحك أعلى موثوقية عندما تكون التكلفة مقبولة.

### 5.3 خط الأنابيب

```
صورة خام
  → كشف البطاقة وقصّها
  → تصحيح المنظور والدوران
  → تحسين الإضاءة والتباين
  → Image Quality Score ──(منخفض)──→ MANUAL_REVIEW
  → OCR (بحسب الوضع)
  → توطين الحقول (layout / anchors / regex)
  → تطبيع (عربي، أرقام، تواريخ)
  → تحقق (checksum، منطق التواريخ)
  → ExtractionResult
```

### 5.4 توطين الحقول

استراتيجية هجينة، لأن كل واحدة منفردة هشّة:
1. **Anchor-based** — البحث عن التسميات (`رقم الإقامة`, `تاريخ الانتهاء`, `المهنة`) ثم أخذ النص المجاور.
2. **Positional template** — قالب إحداثيات لكل إصدار بطاقة بعد المعايرة على عيّناتك.
3. **Regex/Pattern** — رقم الإقامة وأنماط التواريخ تُلتقط بالنمط أياً كان موقعها.
4. **Vision LLM structured output** — استخراج مباشر إلى JSON (في High-Accuracy Mode).

> ⚠️ لا يمكن تثبيت القالب (2) قبل رؤية عيّنة حقيقية. هذا أول ما سنعايره في Phase 4.

## 6. منهجية تصنيف صاحب العمل

### 6.1 المبدأ الحاكم

> **الاسم وحده لا يكفي أبداً للتصنيف `INDIVIDUAL`.** هذه أخطر نقطة في النظام: تصنيف خاطئ هنا يحرم شخصاً من تصريح عمل. لذلك التصنيف تراكمي بالأدلة، والافتراضي عند الشك هو `UNKNOWN` → مراجعة بشرية، وليس الرفض.

### 6.2 سلسلة الإشارات (Signal Cascade)

| الطبقة | الإشارة | القوة | مثال |
|---|---|---|---|
| **L1** | قاعدة مرجعية داخلية (اسم/رقم سجل معروف) | **حاسمة** | مطابقة مؤكدة سابقاً |
| **L2** | كيان حكومي (وزارة، هيئة، أمانة، جامعة، مستشفى حكومي) | قوية | `GOVERNMENT` |
| **L3** | صيغة نظامية للمنشأة | قوية | `شركة`, `مؤسسة`, `مصنع`, `مجموعة`, `مقاولات`, `ذ.م.م`, `مساهمة`, `تضامن`, `Co.`, `Ltd.`, `LLC`, `Est.`, `Group` |
| **L4** | مؤشر نشاط تجاري | متوسطة | `للتجارة`, `للمقاولات`, `للخدمات`, `القابضة` |
| **L5** | مورفولوجيا اسم شخص | **ضعيفة — لا تُستخدم منفردة** | نمط ثلاثي/رباعي + `بن`/`بنت` + بدون أي مؤشر نظامي |
| **L6** | مُحقِّق خارجي (Adapter) | حاسمة | غير مفعّل — مستقبلي |

### 6.3 منطق القرار

```
if  L1 مطابقة              → التصنيف المخزّن            (ثقة 1.00)
elif L2 مؤشر حكومي          → GOVERNMENT                (ثقة 0.95)
elif L3 صيغة نظامية         → COMPANY                   (ثقة 0.90)
elif L4 مؤشر نشاط           → COMPANY                   (ثقة 0.75)
elif L5 اسم شخص + لا شيء آخر → INDIVIDUAL (مبدئي)        (ثقة 0.60) → مراجعة إلزامية
else                        → UNKNOWN                    (ثقة 0.00) → مراجعة إلزامية
```

**العتبة:** `INDIVIDUAL` لا يُنتج رفضاً آلياً إلا إذا تجاوزت الثقة `employer.individual_auto_reject_threshold` (مقترح 0.85 — أي بالكاد يُبلَغ من L5 وحدها؛ عملياً يعني: الرفض الآلي لصاحب عمل فرد يتطلب دليلاً من L1 أو L6). ما دون ذلك → `MANUAL_REVIEW`.

### 6.4 ⚠️ إشكال تعريفي يجب حسمه قبل البناء

كلمة **«مؤسسة»** في السعودية = منشأة مسجّلة بسجل تجاري لكن يملكها **شخص طبيعي واحد** (sole proprietorship). فهل:

- **(أ)** «مؤسسة عبدالله للمقاولات» = `COMPANY` لأنها منشأة نظامية بسجل تجاري؟ أم
- **(ب)** = `INDIVIDUAL` لأن مالكها فرد؟

الفرق بين الخيارين قد يقلب نتيجة نسبة كبيرة من الحالات. **هذا سؤال Q2 وأهم سؤال في الوثيقة.** فهمي المبدئي أن مقصودك بـ «صاحب عمل فرد» هو الشخص الطبيعي الكافل (عمالة منزلية / كفالة شخصية) وليس المؤسسة الفردية — لكنني لن أفترض.

### 6.5 مخرج المصنّف

```json
{
  "employer_raw": "مؤسسة الخليج للمقاولات",
  "employer_type": "COMPANY",
  "confidence": 0.90,
  "evidence": [
    {"layer": "L3", "signal": "legal_form_keyword", "matched": "مؤسسة"},
    {"layer": "L4", "signal": "activity_keyword",  "matched": "للمقاولات"}
  ],
  "rule_version": "employer_rules_v1.2",
  "requires_review": false
}
```

## 7. منهجية تصنيف المهنة

### 7.1 مصدر التصنيف الأساسي

**التصنيف السعودي الموحد للمهن (SSCO)** الصادر عن الهيئة العامة للإحصاء، والمتوائم مع **ISCO-08** — 5 مستويات هرمية، 432 وحدة، ~2013 مهنة. اعتماده كمفتاح أساسي (بدل النص الحر) يعطي:

- مفتاحاً ثابتاً لا يتأثر باختلاف صياغة المسمّى على البطاقة
- إمكانية الاستثناء **على مستوى مجموعة كاملة** بدل تعداد كل مهنة (مثال: استثناء المجموعة الفرعية للعمالة المنزلية دفعةً واحدة)
- توافقاً مع أي تكامل حكومي مستقبلي

### 7.2 خط المطابقة

```
النص الخام
  → تطبيع (إزالة تشكيل/تطويل، توحيد أإآا→ا، ة→ه، ى→ي، توحيد المسافات، تصغير الإنجليزي)
  → 1. مطابقة تامة       → ثقة 1.00
  → 2. جدول المرادفات    → ثقة 0.95   (سائق خاص = سائق منزل = خادم سائق ...)
  → 3. مطابقة ضبابية     → ثقة = درجة التشابه   (≥ العتبة، افتراضياً 0.88)
  → 4. مطابقة جزئية/كلمة مفتاحية → ثقة منخفضة → مراجعة إلزامية
  → 5. لا مطابقة         → UNKNOWN → مراجعة إلزامية
```

> **نقطة تصميم حرجة:** المهنة غير المعروفة **لا تُعتبر مؤهلة تلقائياً**. الافتراض الآمن أن المجهول يُراجَع، لأن العكس (قبول ضمني) يفتح ثغرة تلقائية في كل مرة تظهر مهنة جديدة.

## 10. الأمان والخصوصية

### 10.1 الإطار التنظيمي المُتحقَّق منه

النظام يعالج **بيانات شخصية لمقيمين في السعودية**، فيقع تحت **نظام حماية البيانات الشخصية (PDPL)** بإشراف **سدايا (SDAIA)**.

الأهم عملياً — **نقل البيانات خارج المملكة:**
- منظَّم بلائحة مستقلة تحت PDPL
- يتطلب أساساً نظامياً + ضمانات معتمدة (SCCs أو BCRs) + تقييم أثر للنقل المستمر أو واسع النطاق
- ⚠️ **سدايا لم تنشر بعد قائمة الدول ذات الحماية الكافية** — أي أن كل نقل خارجي عملياً يحتاج ضمانات تعاقدية معتمدة

### 10.2 الأثر المباشر على التصميم

> **هذه هي الحجة الحاسمة لجعل `Local Mode` هو الافتراضي.** استخدام Vision LLM أو OCR سحابي = نقل صور هوية خارج المملكة = التزام تنظيمي كامل عليك. لذلك:

| القرار التصميمي | المبرر |
|---|---|
| `Local Mode` افتراضي، ولا يغادر بايت واحد الجهاز | الامتثال بدون عبء تعاقدي |
| أي Provider خارجي يتطلب **تفعيلاً صريحاً + إقراراً موثّقاً** | لا تسرّب بالخطأ |
| شاشة تحذير عند تفعيل الوضع الخارجي تشرح الالتزام | شفافية |
| تسجيل كل نقل خارجي في سجل التدقيق | إثبات الامتثال |

### 10.3 الضوابط التقنية

| الضابط | التنفيذ |
|---|---|
| **تقليل البيانات** | لا يُستخرج إلا ما تحتاجه القواعد؛ صورة الوجه لا تُخزَّن افتراضياً |
| **التشفير عند التخزين** | AES-256 لرقم الإقامة والاسم وتاريخ الميلاد |
| **التشفير أثناء النقل** | TLS 1.3 |
| **حذف الصور** | افتراضياً بعد المعالجة؛ الاحتفاظ خيار صريح بمدة مُكوَّنة |
| **الإخفاء في السجلات** | رقم الإقامة `2*****789` — **لا يُكتب كاملاً في أي log مطلقاً** |
| **الإخفاء في الواجهة** | حسب الدور؛ الكشف الكامل حدث مُسجَّل في التدقيق |
| **سجل تدقيق** | من/متى/ماذا لكل: رفع، معالجة، تصحيح، تصدير، حذف، تغيير قاعدة — غير قابل للتعديل |
| **حق الحذف** | حذف كامل يشمل الصور والمشتقات والنسخ المؤقتة |
| **الاحتفاظ** | سياسة مدة قابلة للتكوين + حذف تلقائي ⚠️ Q11 |
| **التحكم بالوصول** | RBAC + جلسات + قفل بعد محاولات فاشلة |
| **أمان الرفع** | فحص نوع الملف الحقيقي (magic bytes)، حد الحجم، مسح الملفات المشبوهة |
| **النسخ الاحتياطي** | مشفّر |

### 10.4 اعتبار عدالة القرار

قرار `REJECTED` آلي يؤثر على فرصة عمل شخص حقيقي. أوصي بـ:

1. **تفعيل `require_human_confirmation_on_reject`** على الأقل في المرحلة الأولى حتى تُثبت الدقة إحصائياً
2. **قابلية التتبع الكامل** — أي رفض يجب أن يكون قابلاً للشرح بالقاعدة والمُدخل والدليل
3. **مسار تظلّم/إعادة فحص** موثّق
4. ⚠️ **مراجعة مستشارك القانوني** لمدى انطباق أحكام PDPL المتعلقة بالقرارات الآلية على حالتك — لست جهة إفتاء قانوني

### 12.2 المبادئ المعمارية

| المبدأ | التطبيق |
|---|---|
| **فصل القواعد عن المنطق** | محرك القواعد يقرأ التكوين؛ لا قيمة عمل واحدة في الكود |
| **المحوّلات (Adapters)** | OCR ومصادر التحقق كلها خلف واجهات — التبديل بالتكوين |
| **الفشل الآمن** | كل غموض → مراجعة بشرية، لا قرار آلي |
| **قابلية التفسير** | كل قرار يحمل سلسلة أدلته كاملة |
| **الخصوصية بالتصميم** | محلي افتراضياً، تقليل بيانات، إخفاء تلقائي |
| **الحتمية** | نفس المدخل + نفس إصدار القواعد = نفس المخرج، دائماً |
| **العزل** | كل مستند يُعالَج مستقلاً؛ فشله لا يؤثر على غيره |

### 12.3 تدفق البيانات (مسار واحد)

```
رفع → تخزين مؤقت مشفّر → قياس الجودة
  → معالجة مسبقة → OCR → استخراج حقول (+ثقة +bbox)
  → تحقق وتطبيع
  → [صلاحية] + [صاحب عمل] + [مهنة]   (بالتوازي)
  → محرك القواعد → محرك القرار
  → APPROVED / REJECTED  ──→ حفظ
  → MANUAL_REVIEW ──→ طابور المراجعة ──→ تصحيح ──→ إعادة القرار ──→ حفظ
  → تجميع الدفعة → توليد ملف التصاريح → حذف الصور (حسب السياسة)
                                     → تسجيل التدقيق
```

| # | المخاطرة | الأثر | الاحتمال | المعالجة |
|---|---|---|---|---|

| **R3** | التحويل الهجري ↔ الميلادي غير مطابق للمطبوع | عالٍ (قرار خاطئ في الصلاحية) | متوسط | تفضيل الميلادي المطبوع؛ مقارنة التاريخين؛ التعارض → مراجعة |
| **R4** | تعدد إصدارات بطاقة الإقامة (تخطيطات مختلفة) | متوسط | عالٍ | استخراج قائم على المرساة لا الإحداثيات + قوالب متعددة |

| **R7** | بطاقة مزوّرة | عالٍ | منخفض–متوسط | خارج النطاق حالياً — يجب الإقرار به صراحة |
| **R8** | قوائم المهن غير مكتملة → `UNKNOWN` كثيرة | متوسط (عبء تشغيلي) | عالٍ | البدء من التصنيف السعودي الرسمي + إثراء القاعدة من المراجعات |
| **R9** | عدم توفّر تكامل حكومي رسمي | متوسط | **عالٍ** | التصميم يعمل كاملاً بدونه؛ Adapters جاهزة معطّلة |
| **R10** | مخالفة PDPL عند استخدام OCR سحابي | **عالٍ (تنظيمي)** | متوسط | Local Mode افتراضي + تفعيل صريح + توثيق |
| **R11** | صور رديئة (تصوير بالجوال، ظلال، قصّ ناقص) | متوسط | **عالٍ** | بوابة جودة مبكرة + رسائل إرشادية لإعادة التصوير |
| **R12** | الاعتماد المفرط على النظام وإهمال المراجعة | متوسط | متوسط | إظهار الثقة دائماً + عيّنة تدقيق دورية + عدم إخفاء الغموض |
| **R13** | خوارزمية checksum غير موثّقة رسمياً | منخفض | متوسط | تُستخدم كإشارة ترجيحية فقط، لا كسبب رفض |

### 13.1 القيود المُعلَنة صراحةً

هذه ليست عيوباً قابلة للإصلاح، بل حدود يجب أن يعرفها كل مستخدم:

1. النظام يقرأ **البطاقة**، لا **أنظمة الدولة**.
2. لا يكشف التزوير.
3. لا يتحقق من كون البطاقة تخص حاملها فعلاً.
4. دقته محدودة بجودة الصورة المُدخلة.
5. تصنيف صاحب العمل **تقديري** ما لم يُربط بمصدر رسمي.
6. لا يغني عن التحقق النظامي المطلوب من الجهات المختصة.

> **توصية:** تُطبع هذه القيود في تذييل كل ملف تصاريح.

## 14. الأسئلة والافتراضات التي تحتاج توضيحاً

### 14.1 الأسئلة الحاسمة — تحجب البناء

| # | السؤال | لماذا يحجب |
|---|---|---|
| **Q1** | **هل اسم صاحب العمل مطبوع فعلاً على الإقامات التي تتعامل معها؟ على الوجه الأمامي أم الخلفي؟** أرجو إرسال عيّنة للوجهين (يمكن تمويه الاسم والصورة، مع إبقاء بنية الحقول ظاهرة). | إن لم يكن مطبوعاً، **الفحص الثاني غير قابل للتنفيذ** من الصورة، وتتغير المعمارية |
| **Q2** | **ما تعريفك الدقيق لـ «صاحب عمل فرد»؟** هل «مؤسسة فلان للمقاولات» (سجل تجاري بمالك فرد) = `COMPANY` أم `INDIVIDUAL`؟ | يقلب نتيجة نسبة كبيرة من الحالات |
| **Q3** | **ملف قواعد وأهداف الفحص** الذي وعدت به — هل يمكن إرساله الآن؟ | هو المصدر الرسمي لكل القواعد |
| **Q4** | **هل هناك فحوص إضافية قادمة** (رقم الحدود، رخصة العمل، التأمين، شهادة صحية)؟ | يؤثر على تصميم محرك القواعد من البداية |

### 14.2 أسئلة تشغيلية

| # | السؤال | الافتراض الحالي |
|---|---|---|
| **Q5** | التقويم المرجعي على بطاقاتك: هجري، ميلادي، أم الاثنان؟ وأيهما تعتمده عند التعارض؟ | كلاهما مطبوع؛ الميلادي هو المرجع |
| **Q6** | عتبة `EXPIRING SOON` بالأيام؟ وهل تُعتبر `APPROVED` مع تنبيه أم `REJECTED`؟ | 30 يوماً، `APPROVED` مع تنبيه |
| **Q7** | الحجم المتوقع: كم إقامة في الدفعة؟ وكم يومياً؟ | 100–500 للدفعة، بضع مئات يومياً |
| **Q8** | مكان التشغيل: جهاز محلي، خادم داخلي، أم سحابة؟ وأي منطقة؟ | خادم داخلي / محلي |
| **Q9** | عدد المستخدمين وهل تحتاج أدواراً وصلاحيات؟ | مستخدم واحد في MVP، RBAC لاحقاً |
| **Q10** | لغة الواجهة: عربي، إنجليزي، أم الاثنان؟ | ثنائية اللغة مع RTL |
| **Q11** | مدة الاحتفاظ بالصور والبيانات؟ | حذف الصور فوراً بعد المعالجة، البيانات 12 شهراً |
| **Q12** | هل تُلزم بمراجعة بشرية قبل كل `REJECTED`؟ | نعم في المرحلة الأولى (موصى به) |
| **Q13** | من يستهلك ملف التصاريح: إنسان أم نظام آخر؟ (يحدد الصيغة) | إنسان — Excel |
| **Q14** | مصدر الصور: ماسح ضوئي، كاميرا جوال، أم الاثنان؟ | الاثنان، مع غلبة الجوال |
| **Q15** | هل لديك بالفعل قائمة أصحاب عمل معروفين (أرقام سجلات/أسماء) لبذر القاعدة المرجعية؟ | لا |
| **Q16** | هل حصلت — أو تنوي — على اعتماد رسمي لـ واثق أو مقيم؟ | لا، والتصميم لا يعتمد عليه |

### 14.3 الافتراضات المُعتمَدة حتى تصحّحها

1. الإقامات المُعالَجة **سعودية فقط** — لا هويات وطنية ولا جوازات.
2. الصور بجودة معقولة عموماً؛ الرديء يذهب للمراجعة لا للرفض.
3. لديك **أساس نظامي مشروع** لمعالجة هذه البيانات (عقد، تصريح، موافقة).
4. النظام **مساعد قرار** وليس مُصدِراً نهائياً للتصاريح.
5. لا يوجد تكامل حكومي في MVP.
6. **لا Hard Coding لأي قيمة عمل** — التزام معماري غير قابل للتفاوض.
7. `MANUAL_REVIEW` حالة **مرغوبة** لا فشل — ووجودها بكثرة في البداية أمر طبيعي وصحّي.
